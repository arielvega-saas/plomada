El problema, concreto

Integrar MercadoPago no es difícil por la API. Es difícil por lo que la documentación no dice.

Webhooks sin firmar

En el plan gratuito MercadoPago no firma con HMAC. Si confiás en la notificación, cualquiera paga ARS 1 y se activa tu producto.

Notificaciones duplicadas

Llegan varias por el mismo pago (pending → approved). El dedupe ingenuo hace que el comprador pague y no reciba nada.

Monedas que rechaza

Una cuenta argentina no emite MXN ni EUR. Sin fallback, cada comprador mexicano recibe un 400 y la venta se pierde en silencio.

Reintentos infinitos

Devolver 500 en un pago rechazado deja al proveedor reintentando esa notificación para siempre.

El bug que más caro sale

Este es el orden intuitivo de un webhook. Y está mal.

// ❌ El comprador paga y no recibe nada
const { error } = await db.from("webhook_events").insert({ id: `mp:${paymentId}` });
if (error?.code === "23505") return { alreadyProcessed: true };  // ← sale por acá
const payment = await fetchPayment(paymentId);

La notificación pending ocupa la clave y devuelve. Cuando llega la approved —la única que importa— choca con el unique, la función sale temprano y el acceso no se activa nunca. En los logs todo parece bien: el webhook devolvió 200.

// ✅ Resolver el pago primero; el estado va en la clave
const payment = await fetchPayment(paymentId);        // fuente de verdad
if (payment.status !== "approved") return { ok: false };
const eventId = `mp:${paymentId}:approved`;           // ya no colisiona

Las 7 lecciones que vienen adentro

Ninguna es teórica: salieron de un producto que cobró con los tres rails en simultáneo. Están comentadas en el archivo donde importan.

  1. Resolvé el pago antes de aplicar idempotenciaSi no, el comprador paga y no recibe nada.
  2. Validá el monto antes de dar accesoSin HMAC, el external_reference no alcanza como prueba.
  3. Devolvé 500 solo en errores transitoriosTabla completa de qué status va en cada caso.
  4. Una cuenta argentina solo emite ARS, USD y BRLEl resto necesita fallback o perdés la venta.
  5. Cada rail vuelve por un parámetro distinto?mp=success, ?checkout=success, ?ls=success.
  6. El reembolso siempre tiene que poder revocarVa antes de la validación de monto, no después.
  7. No borres la fila de dedupe cuando algo fallaMarcala. Es tu único panel de salud.

Lo que este kit NO es

Por adelantado, porque se nota en la primera hora:
  • No es un boilerplate completo: no trae auth, landing, dashboard ni emails. Es la capa de pagos.
  • Los tres rails cubren pago único (con cuotas en MercadoPago). Los eventos de suscripción llegan documentados y se ignoran sin romper, pero el que los cablee sos vos.
  • El rate limiting es por proceso: con varias réplicas el techo real es N × tokens. Está documentado y la interfaz permite cambiar a Redis sin tocar los llamadores.
  • La conversión a USD es un snapshot para reportes, no contabilidad.

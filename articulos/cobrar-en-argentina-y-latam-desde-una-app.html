Cómo cobrar en Argentina y LATAM desde tu app: MercadoPago, Stripe o Lemon Squeezy

2026-09-01

La primera pregunta cuando armás un producto digital desde Argentina no es de código: es "¿cómo entra la plata?". Y la respuesta cambia según de dónde venga el que compra, no según lo que a vos te resulte más cómodo integrar.

Después de cablear los tres rails en la misma app y ver cuál cobraba qué, esto es lo que quedó claro.

Lo que hace cada uno, sin marketing

MercadoPago es un procesador. Vos sos el vendedor frente al comprador y frente a AFIP: emitís vos, facturás vos, y el dinero cae en tu cuenta de Mercado Pago, desde donde lo transferís a tu CBU. Acepta los medios de pago que la gente de la región efectivamente usa: dinero en cuenta, tarjetas locales, débito, y cuotas. Ese último punto no es un detalle: en Argentina, un producto de precio medio con cuotas convierte bastante mejor que el mismo producto en un pago.

Stripe es el mejor procesador del mundo por API y documentación, y no opera en Argentina. Para usarlo necesitás una entidad en un país soportado —típicamente una LLC en Estados Unidos, con su cuenta bancaria y sus obligaciones fiscales— y después traer esa plata. Es una decisión contable antes que técnica.

Lemon Squeezy es merchant of record: legalmente el que le vende al comprador es Lemon Squeezy, no vos. Ellos calculan, cobran y declaran el IVA europeo, el sales tax de Estados Unidos y el resto del zoológico impositivo. Vos vendés un producto a Lemon Squeezy y ellos te liquidan. Cobra una comisión bastante más alta que Stripe, y esa diferencia es literalmente el precio de no tener que registrarte en el IVA de la Unión Europea.

Las comisiones cambian seguido en los tres, y en MercadoPago además dependen del plazo de acreditación. No las memorices: mirá tu panel el día que definas el precio.

El límite que casi nadie documenta: MLA solo emite tres monedas

Una cuenta de MercadoPago argentina —site_id MLA— puede crear preferencias en ARS, USD y BRL. Nada más. Si le mandás currency_id: "MXN" o "EUR", la API te devuelve un 400 con currency_id invalid y el comprador ve una pantalla rota.

Lo descubrí de la peor manera: un comprador mexicano llegó al checkout, la app le armó la preferencia en MXN porque su país decía México, y se comió un error 400. Desde afuera se veía como "la página no anda".

La solución no es un mensaje de error más lindo. Es un fallback explícito a USD: el comprador paga en dólares y su tarjeta hace la conversión, que es exactamente lo que pasa cuando compra en cualquier sitio internacional.

// src/lib/mp/monedas.ts
// Verificado contra la API con una cuenta MLA (Argentina).
const MONEDAS_MLA = new Set(["ARS", "USD", "BRL"]);

/** Devuelve la moneda con la que SÍ se puede crear la preferencia. */
export function monedaParaMercadoPago(preferida: string): "ARS" | "USD" | "BRL" {
  const m = preferida.toUpperCase();
  return (MONEDAS_MLA.has(m) ? m : "USD") as "ARS" | "USD" | "BRL";
}

const PRECIO_POR_MONEDA = { ARS: 39900, USD: 39, BRL: 199 } as const;

export function precioPara(paisDelComprador: string) {
  const preferida = paisDelComprador === "AR" ? "ARS"
                  : paisDelComprador === "BR" ? "BRL"
                  : "USD";
  const moneda = monedaParaMercadoPago(preferida);
  return { moneda, monto: PRECIO_POR_MONEDA[moneda] };
}

Ese mismo mapa PRECIO_POR_MONEDA es el que después usa el webhook para validar que el monto pagado cubra el precio oficial. Una sola fuente de verdad, del lado del servidor, para las dos cosas.

Si tu público es mayormente mexicano o colombiano y querés cobrar en moneda local con medios locales, MercadoPago igual es una opción: hay que abrir una cuenta del país correspondiente (MLM para México, MCO para Colombia). Son cuentas separadas, con credenciales separadas, y eso implica presencia fiscal allá. Para la mayoría de los productos digitales chicos, cobrar en USD y dejar que la tarjeta convierta es la decisión correcta.

El retorno del checkout llega distinto en cada rail

Cuando el comprador vuelve a tu sitio, cada rail te avisa con su propio parámetro:

  • MercadoPago: ?mp=success (más los que agrega él: payment_id, status, external_reference, merchant_order_id)
  • Stripe: ?checkout=success
  • Lemon Squeezy: ?ls=success

Es un detalle chico con una consecuencia grande: si tu evento de analytics escucha solamente checkout=success porque arrancaste con Stripe, todas las ventas por MercadoPago desaparecen de tus métricas de conversión. No aparecen mal: no aparecen. Y el banner de "estamos procesando tu pago" tampoco se muestra, así que el usuario aterriza en una pantalla que no le dice nada.

Un solo lector para los tres:

// src/lib/pagos/retorno.ts
const RAILS = [
  { param: "mp",       rail: "mercadopago"  },
  { param: "checkout", rail: "stripe"       },
  { param: "ls",       rail: "lemonsqueezy" },
] as const;

export type Retorno = {
  rail: (typeof RAILS)[number]["rail"];
  estado: "success" | "pending" | "failure" | "cancel";
};

export function leerRetorno(sp: URLSearchParams): Retorno | null {
  for (const { param, rail } of RAILS) {
    const v = sp.get(param);
    if (v) return { rail, estado: v as Retorno["estado"] };
  }
  return null;
}
// src/app/gracias/page.tsx
export default async function Gracias({ searchParams }: { searchParams: Promise<Record<string, string>> }) {
  const retorno = leerRetorno(new URLSearchParams(await searchParams));
  if (!retorno) return <Generico />;

  // Una sola llamada de analytics, con el rail como dimensión.
  return (
    <>
      <TrackCheckout rail={retorno.rail} estado={retorno.estado} />
      {retorno.estado === "success" && <Confirmado />}
      {retorno.estado === "pending" && <Procesando />}   {/* efectivo, transferencia */}
      {(retorno.estado === "failure" || retorno.estado === "cancel") && <Reintentar />}
    </>
  );
}

El estado pending merece su propia pantalla y casi nadie la hace. En Argentina una parte real de los pagos se hacen en efectivo en un Rapipago o por transferencia, y se acreditan horas después. Si a esa gente le mostrás "pago fallido", la perdiste; si le mostrás "recibimos tu pago, te avisamos por mail cuando se acredite", la conservás.

Y lo más importante de toda esta sección: la URL de retorno no es prueba de pago. Cualquiera puede escribir /gracias?mp=success en la barra de direcciones. Sirve para decidir qué pantalla mostrar y qué evento disparar, nunca para otorgar acceso. El acceso lo da el webhook, del lado del servidor, después de re-consultar el pago contra la API. Si tu página de gracias hace un INSERT, tenés un producto gratis.

Cuál elegir

Vendés sobre todo en Argentina. MercadoPago, y ni lo pienses. Es el único que acepta dinero en cuenta y cuotas, y el único que deposita en tu CBU sin intermediarios. El costo es que la parte fiscal la manejás vos.

Vendés al mundo, en dólares, y tenés o vas a tener una LLC. Stripe. Mejor API, mejores herramientas de facturación y suscripciones, comisión más baja. Es más trabajo de setup societario y contable, no de código.

Vendés al mundo y no querés saber nada con impuestos ni sociedades. Lemon Squeezy. Pagás más comisión y te ahorrás el problema entero. Para un producto de un solo desarrollador es, casi siempre, la mejor relación esfuerzo/resultado para el mercado internacional.

Vendés en Argentina y afuera. Los dos: MercadoPago para el mercado local y uno de los otros para el resto. Es la combinación que más vi funcionar, y es también la que más código tonto genera si no la unificás. Lo que hay que abstraer es lo mínimo: una función crearCheckout(rail, producto, usuario), un webhook por rail, y una sola función activarAcceso(compra) que los tres llaman. Todo lo demás es específico de cada rail y tratar de unificarlo te va a doler más que duplicarlo.

Los tres rails con esa forma —checkout unificado, un webhook por rail, una sola activación idempotente sobre Supabase— vienen armados en Pagos LATAM Kit para Next.js.

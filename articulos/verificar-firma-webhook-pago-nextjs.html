Verificar la firma de un webhook de pago en Next.js: el body crudo y los tres errores que se pagan caro

2026-09-05

Hay dos formas de equivocarse verificando la firma de un webhook de pago, y solo una hace ruido.

La ruidosa es este mensaje, que vas a ver la primera tarde:

No signatures found matching the expected signature for payload

La silenciosa es no verificar nada. Tu endpoint de webhook es una URL pública que acepta POST y activa productos. El cuerpo del request lo escribe quien quiera. Sin firma, la única barrera entre un desconocido y una cuenta premium gratis es que no adivine el formato de tu JSON, y el formato de tu JSON está documentado por el proveedor.

Esta nota es cómo verificar bien, con los tres errores que hacen que la firma no valide y el cuarto que hace que valide de más.

Antes que nada: los tres firman, y cada uno firma otra cosa

Es la primera cosa que hay que saber, porque cambia toda la defensa.

RailQué firmaHeaderTu defensa
Stripeel body crudostripe-signature (t= + v1=)verificar la firma
Lemon Squeezyel body crudox-signature (HMAC-SHA256 hex)verificar la firma
MercadoPagoun manifest armado con el data.id, el x-request-id y el ts — no el bodyx-signature (ts= + v1=)verificar la firma y validar el monto
Corrección (2026-09-05). Una versión anterior de esta nota decía que MercadoPago no firmaba. Es falso: MercadoPago documenta x-signature con HMAC-SHA256 desde enero de 2024, y el secreto se saca de Your integrations → tu aplicación → Webhooks. Si estás siguiendo esta guía y no ves el header, revisá que el secreto esté generado en el panel antes de concluir que tu rail no firma. Lo dejamos escrito en vez de editarlo en silencio porque el error tenía consecuencia: hacía parecer opcional un control que no lo es.

MercadoPago tiene una particularidad que conviene entender: no firma el cuerpo. Firma un manifest con tres campos. Eso significa que la firma te prueba que esa notificación, sobre ese id, salió de MercadoPago — pero no te dice nada del monto, porque el monto no viaja firmado. Por eso en MP la firma no reemplaza la validación de monto: hay que hacer las dos. El detalle está en la guía de integración de MercadoPago.

Error 1: leer el body con req.json()

Es el que produce el mensaje de arriba, y el que más tiempo consume, porque el código parece impecable.

La firma se calcula sobre los bytes exactos que el proveedor te mandó. Si hacés await req.json() y después volvés a serializar para verificar, estás firmando otro texto: JSON.stringify no garantiza el mismo orden de claves, no conserva los espacios, y convierte los números a su representación canónica. Un solo byte distinto y el digest no coincide. Nunca. No es intermitente ni depende del entorno: no valida jamás.

La regla es leer el texto una vez, verificar sobre ese texto, y recién después parsearlo.

// src/app/api/webhooks/stripe/route.ts
export const runtime = "nodejs";        // node:crypto — ver el final de la nota
export const dynamic = "force-dynamic"; // nunca cachear un webhook

export async function POST(req: Request) {
  const rawBody = await req.text();                    // ← el texto EXACTO
  const firma = req.headers.get("stripe-signature");

  const v = await verifyEvent(rawBody, firma);
  if (!v.ok) {
    // 400 a propósito: un 500 haría que el proveedor reintente para siempre
    // un evento que nunca va a validar.
    return Response.json({ error: v.reason }, { status: 400 });
  }

  // Recién acá el contenido es confiable.
  return procesar(v.event);
}

Dos trampas de Next.js alrededor de esto:

  • No podés leer el body dos veces. Si algún middleware o helper ya consumió el stream, req.text() devuelve vacío y la firma falla con el mismo mensaje. Si necesitás el objeto, parseá el texto: JSON.parse(rawBody).
  • En el Pages Router hay que apagar el body parser (export const config = { api: { bodyParser: false } }) y leer el stream a mano. En App Router no hace falta: req.text() ya te da el crudo.

Error 2: el secreto equivocado

El segundo error no rompe en producción, rompe en tu máquina, y consume una tarde entera porque el mensaje de error es idéntico al del error 1.

En Stripe, whsec_… no es uno por cuenta: es uno por endpoint. Y el que te imprime stripe listen cuando reenviás eventos a localhost es otro distinto de los del Dashboard.

DóndeQué secreto va
Local con stripe listen --forward-to localhost:3000/api/webhooks/stripeEl whsec_ que imprime ese comando
Preview / stagingEl del endpoint de staging del Dashboard
ProducciónEl del endpoint de producción del Dashboard

Copiar el de producción a .env.local es el camino corto a "mi código anda en prod y no anda en mi máquina". En Lemon Squeezy el secreto lo elegís vos al crear el webhook, así que el problema es el inverso: es fácil dejar el mismo string en los tres entornos y descubrir tarde que un evento de test activó una cuenta real.

Y lo obvio que igual conviene decir: STRIPE_WEBHOOK_SECRET y LEMONSQUEEZY_WEBHOOK_SECRET son server-only. Ninguna lleva prefijo NEXT_PUBLIC_. Una variable con ese prefijo termina en el bundle del navegador, que cualquiera lee con dos clics.

Error 3: comparar el digest con ===

Cuando el proveedor te manda un HMAC pelado —el caso de Lemon Squeezy—, lo tenés que calcular y comparar vos. La forma intuitiva:

// ❌ MAL
return digestCalculado === firmaRecibida;

=== sobre strings corta en el primer byte distinto. El tiempo que tarda en devolver false depende de cuántos caracteres coincidieron. Con suficientes intentos medidos, eso filtra el digest byte por byte. Es un ataque incómodo de montar sobre internet y trivial si el atacante está cerca de tu infraestructura, y arreglarlo cuesta tres líneas.

import { createHmac, timingSafeEqual } from "node:crypto";

export function verifyWebhookSignature(
  rawBody: string,
  signature: string | null | undefined,
): boolean {
  const secret = process.env.LEMONSQUEEZY_WEBHOOK_SECRET;
  if (!secret || !signature) return false;
  try {
    const digest = createHmac("sha256", secret).update(rawBody, "utf8").digest("hex");
    const recibida = signature.trim().toLowerCase();
    // timingSafeEqual LANZA si los buffers miden distinto: la longitud se
    // compara antes. Esa comparación no filtra nada útil — la longitud de un
    // digest hex de SHA-256 es pública: siempre 64.
    if (recibida.length !== digest.length) return false;
    return timingSafeEqual(Buffer.from(digest, "utf8"), Buffer.from(recibida, "utf8"));
  } catch {
    // Fail-closed: cualquier cosa rara (secreto con encoding inválido, header
    // con bytes no-ASCII) es firma inválida. Nunca "pasá igual".
    return false;
  }
}

Ese catch que devuelve false es la parte que más se olvida. Un throw sin capturar en el handler se convierte en un 500, y un 500 le dice al proveedor "reintentá": vas a tener un evento inválido golpeando tu endpoint indefinidamente.

En Stripe no hace falta escribir nada de esto. constructEventAsync parsea el header —que trae el timestamp y una o varias firmas v1, porque durante una rotación de secreto conviven dos—, compara en tiempo constante y aplica una tolerancia temporal. Reescribirlo a mano es exactamente el tipo de código donde el bug no se ve hasta que alguien se activa el producto gratis.

El cuarto: el replay, que valida de más

Los tres anteriores hacen que una firma buena sea rechazada. Este es el opuesto: una firma legítima aceptada dos veces.

Un webhook firmado es una prueba de que ese cuerpo salió del proveedor. No es una prueba de que salió recién. Si alguien captura un checkout.session.completed válido y lo reenvía cien veces, las cien firmas son correctas.

Stripe corta la mayor parte de eso con el timestamp del header y una ventana de tolerancia: un evento viejo no valida. En un HMAC pelado como el de Lemon Squeezy no hay timestamp, así que la firma sola no te protege del reenvío.

Lo que te protege en los dos casos es la idempotencia, y por eso no es una optimización sino un control de seguridad: si el reclamo del pago es atómico y la clave es el id del pago —no el id del evento—, el reenvío número cien encuentra la fila ya reclamada, devuelve 200 y no activa nada. El detalle de ese reclamo está en la nota sobre idempotencia.

Node o Edge: elegí antes de escribir

node:crypto no existe en el Edge runtime. Si tu handler usa createHmac, la route necesita export const runtime = "nodejs".

Si necesitás Edge, la alternativa es crypto.subtle de Web Crypto, que también compara en tiempo constante pero es asíncrona:

const key = await crypto.subtle.importKey(
  "raw", new TextEncoder().encode(secret),
  { name: "HMAC", hash: "SHA-256" }, false, ["verify"],
);
const ok = await crypto.subtle.verify("HMAC", key, firmaBytes, new TextEncoder().encode(rawBody));

Con el SDK de Stripe, la variante constructEventAsync es la que funciona en los dos: en Node usa el crypto nativo y en Edge/Workers usa Web Crypto. La versión sincrónica tira SubtleCrypto is only available async justo en el entorno donde la desplegaste.

El test que parece probar la firma y no prueba nada

Este es el que nos pasó a nosotros, y lo contamos porque es fácil de repetir.

Para testear el motor del webhook sin variables de entorno, le inyectamos el verificador como dependencia y en los tests le pasamos uno falso: firma correcta, evento válido; firma incorrecta, rechazo. El archivo entero en verde.

Lo que esos tests prueban es que el motor reacciona bien a una firma rechazada. No prueban que la verificación funcione. Con el verificador real mutado a un JSON.parse —o sea, aceptando cualquier cosa— seguían todos en verde.

El arreglo es un archivo aparte que ejercita la implementación real, firmando el payload con el secreto de prueba y comprobando los dos lados: que la firma válida pase y que cada mutación (secreto distinto, un byte cambiado en el body, header ausente, timestamp fuera de tolerancia) no pase.

it("un byte cambiado en el body invalida la firma", async () => {
  const body = JSON.stringify({ id: "evt_1", type: "checkout.session.completed" });
  const firma = firmarComoStripe(body, SECRETO);           // implementación real
  expect((await verifyEvent(body, firma)).ok).toBe(true);
  expect((await verifyEvent(body + " ", firma)).ok).toBe(false);
});

La regla general: si podés romper la implementación y tus tests siguen verdes, tus tests no la están probando. Vale para la firma, para la validación de monto y para cualquier control que separe tu producto de la gente que no pagó.

Checklist

  • El handler lee await req.text() antes que nada, y parsea después de verificar.
  • El secreto es el del endpoint que estás usando (el de stripe listen es otro).
  • Ninguna variable de webhook lleva NEXT_PUBLIC_.
  • La comparación de digests es en tiempo constante, con la longitud chequeada antes.
  • El verificador nunca lanza: cualquier error es firma inválida.
  • Firma inválida devuelve 400, no 500.
  • Hay idempotencia por id del pago, que es lo que corta el replay.
  • Existe al menos un test contra la implementación real de verificación, no contra un doble.

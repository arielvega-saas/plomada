El bug de los centavos: monedas sin decimales y el pago de CLP 15.000 que tu app lee como 150

2026-09-05

Un comprador chileno paga CLP 15.000. Tu webhook recibe amount_total: 15000, lo divide por 100 como hace con todo, le da 150, lo compara contra tu precio de 15.000 y lo rechaza. El comprador pagó y ve un error. En tus logs figura "monto insuficiente", que es la mentira más convincente posible: parece que el tipo intentó estafarte.

El mismo bug en la otra dirección es peor. Una orden de Lemon Squeezy llega con subtotal: 1900 —diecinueve dólares en centavos— y tu código la compara contra el 19 del catálogo. Diecinueve es mayor o igual que diecinueve, así que también entra una orden de 19 centavos. Ahí no hay error en ningún log: hay un usuario premium que pagó el uno por ciento.

Los dos salen de lo mismo: cada rail de pago habla en una escala distinta y ninguno te avisa cuál.

Tres rails, tres convenciones. Y la de Stripe no es una regla fija: depende de la moneda. En USD la unidad mínima es el centavo, así que 1900 son diecinueve dólares. En CLP no hay centavos: la unidad mínima es el peso, y 15000 son quince mil pesos. El / 100 que funciona en USD destruye el número en CLP.

La lista, y la trampa que trae adentro

Stripe llama zero-decimal a las monedas donde el monto va tal cual, sin multiplicar. Las que importan si vendés en la región o en Asia:

export const ZERO_DECIMAL_CURRENCIES = new Set([
  "BIF", "CLP", "DJF", "GNF", "JPY", "KMF", "KRW", "MGA",
  "PYG", "RWF", "VND", "VUV", "XAF", "XOF", "XPF",
]);

export function isZeroDecimal(currency: string): boolean {
  return ZERO_DECIMAL_CURRENCIES.has(currency.toUpperCase());
}

Para LATAM las dos que cuentan son CLP (peso chileno) y PYG (guaraní). Ojo con las que parecen candidatas y no lo son: el peso colombiano (COP) y el peso argentino (ARS) tienen dos decimales para Stripe, aunque nadie en la calle pague con centavos.

Y acá está la trampa: hay monedas que son cero decimales en la vida real y no lo son para la API. Stripe las agrupa como "special cases". Sus palabras sobre el chelín ugandés: la moneda pasó a ser de cero decimales, pero por compatibilidad hacia atrás hay que representarla como valor de dos decimales, siempre terminado en 00. O sea que UGX 5 se manda y se recibe como 500. Lo mismo con la corona islandesa (ISK), y HUF y TWD tienen su propia regla para payouts.

Esas cuatro —ISK, HUF, TWD, UGX— van fuera de la lista, aunque tu intuición y la Wikipedia digan lo contrario.

Cómo lo tuvimos mal nosotros

Escribiendo esta nota encontramos que UGX estaba dentro de nuestra propia lista. El comentario del archivo decía, textual, que las special cases no iban ahí; el código las incluía igual. Un comentario correcto arriba de un Set equivocado.

El efecto no era cosmético. Con UGX marcada como cero decimales, un pago de UGX 5 llega como 500, el conversor a unidades mayores devuelve 500 en vez de 5, y la validación de monto compara 500 contra tu precio y aprueba. Acceso otorgado por la centésima parte del precio: justo el agujero contra el que existe ese archivo, en la dirección que regala el producto.

No es una moneda de nuestro mercado, y por eso mismo vale contarlo: los bugs de escala no viven donde mirás. Sobrevivió a la revisión adversarial del código porque el comentario decía lo correcto y nadie contrastó la lista contra la documentación. El arreglo fueron dos líneas y dos tests; encontrarlo llevó escribir un artículo.

Vale tenerlas separadas en la cabeza, porque se detectan de forma distinta.

La conversión, en un solo lugar

La regla que hace que esto no vuelva: el / 100 no se escribe nunca a mano. Vive en dos funciones y todo lo demás las llama.

/** Unidades mínimas del proveedor → unidades mayores (las del catálogo). */
export function toMajorUnits(amountMinor: number, currency: string): number {
  return isZeroDecimal(currency) ? amountMinor : amountMinor / 100;
}

/** Unidades mayores (catálogo) → unidades mínimas del proveedor. */
export function toMinorUnits(amountMajor: number, currency: string): number {
  return Math.round(isZeroDecimal(currency) ? amountMajor : amountMajor * 100);
}

El Math.round de la segunda no es decoración. 19.99 * 100 en punto flotante da 1998.9999999999998, y Math.floor de eso te cobra un centavo de menos: no rompe nada, pero desalinea todos tus totales contra los del proveedor y hace imposible conciliar.

Con eso, la validación de monto se escribe igual para todos los rails:

const pagado = toMajorUnits(sesion.amount_total, sesion.currency);
const minimo = minPriceFor(planId, sesion.currency);   // catálogo, unidades mayores
if (minimo === undefined || !(pagado >= minimo)) {
  return { ok: false, error: "rejected_amount" };      // se audita, NO se activa
}

Dos detalles de esas dos líneas:

  • >= y no ==: las cuotas con interés y las conversiones de moneda pueden dejar unos centavos a tu favor, y un == estricto rechazaría esa venta.
  • La forma negada !(pagado >= minimo) y no pagado < minimo: si pagado es NaN —porque el campo vino null o como string—, < devuelve false y el pago pasa. La forma negada devuelve true y lo rechaza. Es un carácter de diferencia entre fallar cerrado y fallar abierto.

Y el monto tiene que salir de la fuente correcta. En los rails que firman el webhook, el body verificado sirve —de eso trata la nota sobre verificación de firma—. En MercadoPago el monto hay que ir a buscarlo a la API igual, porque MP firma un manifest con el id de la notificación y no el cuerpo: la firma prueba el origen, no el importe. Está en la guía de integración.

El segundo bug, el que no rompe nada

Resuelta la validación, queda uno más silencioso todavía: la escala del libro de revenue.

Si guardás cada transacción "en la unidad mínima del proveedor", CLP 15.000 entra como 15000 y USD 19 como 1900. Los dos números son correctos y son incomparables. El día que sumes revenue total vas a sumar dos escalas distintas, y ningún test va a fallar, porque no hay nada que falle: es una suma de enteros que da un entero.

La salida es elegir una escala para el libro y convertir al entrar, sin excepciones:

/** El libro guarda SIEMPRE centésimos de la unidad mayor, incluso en
 *  monedas de cero decimales. Es la única forma de que sumar sea válido. */
export function toLedgerCents(amountMajor: number): number {
  return Math.round(amountMajor * 100);
}

Con eso, CLP 15.000 se guarda como 1500000 y el mismo importe cobrado por MercadoPago también. Suenan raros esos ceros de más para una moneda sin centavos; es el precio de que la columna se pueda sumar.

Y una advertencia que vale para cualquier reporte multi-moneda: convertir a USD con una tabla de tipos de cambio te sirve para BI agregado, no para contabilidad. Para cifras contables va el monto liquidado que informa el proveedor, que ya tiene su spread adentro.

Los tests que lo agarran

Tres, y son cortos:

it("ida y vuelta en las dos escalas", () => {
  expect(toMajorUnits(1900, "USD")).toBe(19);
  expect(toMinorUnits(19, "USD")).toBe(1900);
  expect(toMajorUnits(15000, "CLP")).toBe(15000);   // sin decimales
  expect(toMinorUnits(15000, "CLP")).toBe(15000);
});

it("las special cases NO son cero decimales", () => {
  for (const c of ["ISK", "HUF", "TWD", "UGX"]) {
    expect(isZeroDecimal(c)).toBe(false);
    expect(toMajorUnits(500, c)).toBe(5);
  }
});

it("el libro guarda siempre centésimos", () => {
  expect(toLedgerCents(toMajorUnits(15000, "CLP"))).toBe(1500000);
  expect(toLedgerCents(toMajorUnits(1900, "USD"))).toBe(1900);
});

El del medio es el que hubiera encontrado nuestro bug de UGX el primer día. No prueba una función complicada: prueba que una lista de datos coincida con la documentación del proveedor, que es donde viven los errores que ninguna revisión de lógica encuentra.

Cómo revisarlo en tu app, ahora

Sin desplegar nada:

  1. Buscá / 100 y * 100 en tu código. Cada aparición que no esté dentro de una función que reciba la moneda es un candidato.
  2. Andá a la lista de monedas de tu catálogo. Si hay CLP, PYG, JPY o KRW, el bug ya está ahí esperando el primer comprador de ese país.
  3. Comprobá tu comparación de monto: si dice pagado < minimo, cambiala a !(pagado >= minimo).
  4. Mirá una fila real de tu tabla de transacciones en cada moneda y preguntate si esas dos filas se pueden sumar.

Integrar MercadoPago en Next.js (App Router): la guía que me hubiera ahorrado tres días

2026-09-01

Un usuario compró. En el panel de MercadoPago el pago figura approved. En mi base no hay nada, y el tipo me escribe por mail preguntando dónde está lo que pagó.

Ahí termina casi toda primera integración de MercadoPago: el checkout anda, el dinero entra, la activación no ocurre. No es un bug de una línea: son tres decisiones de diseño que la documentación oficial no pone juntas en ninguna página. Esta guía cubre las tres.

Por qué no vas a usar el SDK oficial

El paquete mercadopago de npm es CommonJS y toca APIs de Node que el Edge runtime no tiene. Si tu route handler corre en Edge —o si el módulo termina importado desde el middleware, cosa fácil de que pase sin querer— el build falla, o rompe en runtime con un error que no menciona a MercadoPago por ningún lado.

Podés fijar export const runtime = "nodejs" y sobrevivir. Pero mirá lo que necesitás del SDK: dos endpoints REST. Con fetch corre igual en Node, Edge y Workers, y no heredás los breaking changes entre la v1 y la v2.

// src/lib/mp/client.ts
export type MpPayment = {
  id: number;
  status: "pending" | "approved" | "rejected" | "cancelled" |
          "refunded" | "charged_back" | (string & {});
  external_reference: string | null;
  transaction_amount: number;
  currency_id: string;
};

export async function getPayment(id: string): Promise<MpPayment | null> {
  const res = await fetch(`https://api.mercadopago.com/v1/payments/${id}`, {
    headers: { Authorization: `Bearer ${process.env.MP_ACCESS_TOKEN}` },
    cache: "no-store",
  });
  if (res.status === 404) return null;   // todavía no visible: es transitorio
  if (!res.ok) throw new Error(`MP ${res.status}: ${await res.text()}`);
  return (await res.json()) as MpPayment;
}

Fijate el (string & {}) al final del union. MercadoPago agrega estados nuevos sin avisar, y un enum cerrado te rompe el parseo entero cuando aparece uno que no conocías: ese día perdés todas las notificaciones, no solo la rara.

Paso 1: crear la preferencia

La preferencia describe qué se vende y a dónde vuelve el comprador. Se crea en tu servidor: el access_token no puede salir del backend.

// src/lib/mp/preference.ts
import { randomUUID } from "node:crypto";

export async function createPreference(args: {
  userId: string; title: string;
  unitPrice: number; currencyId: "ARS" | "USD" | "BRL";
}) {
  const externalReference = `${args.userId}:${randomUUID()}`;
  const base = process.env.NEXT_PUBLIC_SITE_URL!; // https, absoluto, sin barra final

  const res = await fetch("https://api.mercadopago.com/checkout/preferences", {
    method: "POST",
    cache: "no-store",
    headers: {
      Authorization: `Bearer ${process.env.MP_ACCESS_TOKEN}`,
      "Content-Type": "application/json",
      "X-Idempotency-Key": externalReference,
    },
    body: JSON.stringify({
      items: [{ title: args.title, quantity: 1,
                unit_price: args.unitPrice, currency_id: args.currencyId }],
      external_reference: externalReference,
      notification_url: `${base}/api/webhooks/mercadopago`,
      back_urls: {
        success: `${base}/gracias?mp=success`,
        pending: `${base}/gracias?mp=pending`,
        failure: `${base}/checkout?mp=failure`,
      },
      auto_return: "approved",
    }),
  });

  if (!res.ok) throw new Error(`No pude crear la preferencia: ${await res.text()}`);
  const pref = (await res.json()) as { id: string; init_point: string };
  return { checkoutUrl: pref.init_point, externalReference };
}

Tres detalles que cuestan una tarde cada uno:

  • auto_return: "approved" exige que back_urls.success sea absoluta y https. Con http://localhost:3000 devuelve auto_return invalid. back_url.success must be defined, un mensaje que apunta al campo equivocado.
  • notification_url también tiene que ser pública. localhost no existe para los servidores de MercadoPago. cloudflared tunnel --url http://localhost:3000 te da una URL gratis y sin cuenta.
  • El external_reference es tu única forma de saber quién compró. No confíes en que el email del pagador coincida con el de tu cuenta: mucha gente paga con el Mercado Pago de la pareja.

El front solo redirige a checkoutUrl: no hace falta el SDK de JavaScript ni el Wallet Brick para arrancar.

Paso 2: el webhook, y el orden que importa

Acá está el bug que hace que el usuario pague y no reciba nada.

MercadoPago manda varias notificaciones por el mismo pago mientras el pago cambia de estado: una en pending, otra en approved, a veces una tercera de reintento. Todas con el mismo data.id.

La intuición dice: primero deduplico, después trabajo. Eso es exactamente lo que rompe. La de pending llega primero e inserta la fila de deduplicación; cuando llega la de approved —la única que importa— el INSERT choca contra el unique y devuelve 23505. El código la descarta como "duplicada" y el acceso nunca se activa. La secuencia medida y el reclamo atómico en SQL, en esta nota.

El orden correcto es al revés: resolvé el pago primero, deduplicá después.

// src/app/api/webhooks/mercadopago/route.ts
export const runtime = "nodejs";
export const dynamic = "force-dynamic";

export async function POST(req: Request) {
  const url = new URL(req.url);
  const body = await req.json().catch(() => ({} as any));
  const topic = body?.type ?? url.searchParams.get("type") ?? url.searchParams.get("topic");
  const paymentId = body?.data?.id ?? url.searchParams.get("data.id");

  // merchant_order y otros tópicos: no son error, no los usamos.
  if (topic !== "payment" || !paymentId) return json(200, { ignored: topic ?? null });

  // 1. RESOLVER: el estado real sale de la API, no del body.
  const pago = await getPayment(String(paymentId));
  if (!pago) return json(500, { retry: "todavía no visible en la API" });

  // 2. FILTRAR: solo approved sigue.
  if (pago.status !== "approved") return json(200, { skipped: pago.status });

  // 3. VALIDAR EL MONTO, antes de tocar nada.
  if (!montoCubrePrecio(pago)) return json(200, { rejected: "monto insuficiente" });

  // 4. RECIÉN AHORA: idempotencia.
  const claim = await reclamarPago("mercadopago", String(pago.id), pago);
  if (!claim.reclamado) return json(200, { already: true });

  try {
    await activarAcceso(pago);
    await claim.confirmar();
    return json(200, { ok: true });
  } catch (e) {
    await marcarFallido("mercadopago", String(pago.id), String(e));
    return json(500, { retry: "no pude activar el acceso" });
  }
}

Paso 3: validar el monto, siempre

En la cuenta con la que probé, las notificaciones llegaban sin header x-signature: la firma HMAC no está disponible en todos los planes. Si la tuya la manda, validala. Pero no puede ser tu único control, porque el día que no venga te quedás sin ninguno.

El control que siempre podés hacer es el aritmético. Un external_reference válido solo prueba que alguien conoce ese string. Si verificás nada más que eso, cualquiera abre el checkout, paga ARS 1 y se activa el producto.

// src/lib/mp/precios.ts — una sola fuente de verdad, del lado del servidor
const PRECIO: Record<string, number> = { ARS: 39900, USD: 39, BRL: 199 };

export function montoCubrePrecio(p: MpPayment): boolean {
  const oficial = PRECIO[p.currency_id];
  if (oficial === undefined) return false;       // moneda que no vendemos
  return p.transaction_amount + 0.01 >= oficial; // tolerancia de redondeo
}

El monto sale de la API, no del body. Esa diferencia es toda la seguridad del esquema: el body lo escribe cualquiera que conozca tu URL, la respuesta de GET /v1/payments/:id no.

Paso 4: qué status HTTP devolver

MercadoPago reintenta cuando tu endpoint responde algo que no es 2xx. Es una funcionalidad excelente y una trampa a la vez: un 500 mal puesto te genera reintentos infinitos sobre un caso que nunca va a mejorar.

La regla: 500 significa "volvé a intentar, esto puede cambiar". Nada más.

SituaciónStatusPor qué
Pago todavía no visible en la API (404)500Es una carrera; en 10 segundos existe
Falló activar (DB caída, timeout, excepción)500Transitorio, el reintento lo resuelve
Ya procesado (idempotencia)200Reintentar no cambia nada
rejected, cancelled o monto insuficiente200Terminal, no va a mejorar
Tópico que no manejamos, o body sin data.id200No hay nada que reintentar

Y respondé rápido: si tu handler tarda, MercadoPago corta la conexión y lo cuenta como fallo, aunque hayas activado todo bien. Si la activación manda mails, encolá eso y respondé.

Cómo probarlo sin adivinar

Levantá el túnel, poné esa URL en notification_url y pagá de verdad, con el monto mínimo que acepte tu cuenta y desde otra cuenta: el sandbox no reproduce la secuencia de notificaciones múltiples, que es justo el caso que rompe. Loggeá cada notificación con data.id, el status que devolvió la API y el status HTTP con el que respondiste.

Después reenviá a mano la misma notificación tres veces: tienen que salir tres 200 y un solo acceso activado. Ese es el test de aceptación de toda la integración.

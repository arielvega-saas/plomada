El bug de idempotencia que hace que tu usuario pague y no reciba nada

2026-09-01

El síntoma es siempre el mismo y siempre tarda un día en aparecer, porque necesita tráfico real: el pago está approved en el panel de MercadoPago, el dinero entró, y el usuario no tiene acceso a nada. En los logs hay una sola línea útil:

duplicate key value violates unique constraint "pagos_procesados_pkey" (SQLSTATE 23505)

Y el handler la trata como éxito, porque "ya estaba procesado". Nunca estuvo procesado. Se procesó la notificación equivocada.

MercadoPago no manda una notificación por pago

Manda varias, por el mismo pago, a medida que el pago cambia de estado. Es correcto que lo haga —así te enterás de un contracargo tres semanas después— pero rompe la suposición de que un data.id equivale a un evento.

Esta es la secuencia real de una compra con tarjeta, medida con logs en producción:

t=0.0s  el usuario confirma el pago en el checkout
t=0.4s  MP  ──POST /api/webhooks/mercadopago──▶  { type:"payment", data:{ id:"128744391" } }
             tu handler: GET /v1/payments/128744391  →  status: "pending"

t=2.9s  el emisor de la tarjeta aprueba

t=3.1s  MP  ──POST /api/webhooks/mercadopago──▶  { type:"payment", data:{ id:"128744391" } }
             ▲ MISMO data.id, distinto significado
             tu handler: GET /v1/payments/128744391  →  status: "approved"

t=9.6s  MP  ──POST /api/webhooks/mercadopago──▶  { type:"payment", data:{ id:"128744391" } }
             (reintento / duplicado; MP no garantiza entrega única)
             tu handler: GET /v1/payments/128744391  →  status: "approved"

Tres POST. Un data.id. Y solo el segundo es el que tiene que activar el acceso.

El código que parece bien y no lo está

// ❌ Este es el bug. La idempotencia va primero.
export async function POST(req: Request) {
  const { data } = await req.json();

  // "Que no se procese dos veces."
  const { error } = await supabase
    .from("pagos_procesados")
    .insert({ rail: "mercadopago", payment_id: String(data.id) });

  if (error?.code === "23505") return new Response("ok", { status: 200 }); // ya procesado
  if (error) return new Response("error", { status: 500 });

  const pago = await getPayment(String(data.id));
  if (pago?.status === "approved") await activarAcceso(pago);

  return new Response("ok", { status: 200 });
}

Seguí la secuencia de arriba con ese código en la mano:

  • t=0.4s — inserta la fila. Consulta la API: pending. No activa nada. La fila queda, mintiendo: dice "procesado" y no se procesó nada.
  • t=3.1s — el INSERT choca con 23505. Devuelve 200 y corta. Nunca consulta la API. Nunca ve el approved.
  • t=9.6s — igual que la anterior.

Resultado: el usuario pagó, tu servidor respondió 200 tres veces, MercadoPago considera la entrega exitosa y no va a reintentar más nunca. El acceso no existe y no hay ningún error en tus logs, porque el 23505 lo estás tratando como camino feliz.

Es un bug silencioso: no se detecta con monitoreo, se detecta con un mail enojado.

Por qué la intuición falla

La idempotencia protege contra entregar dos veces el mismo efecto. Pero acá el data.id no identifica un efecto: identifica un recurso que va cambiando. Deduplicar por el id del pago antes de saber en qué estado está es deduplicar en el momento equivocado.

La regla que se generaliza a cualquier rail: la clave de idempotencia identifica la transición que te importa, no la notificación. Si tu clave es el id del pago, el gate va después de haber decidido que ese pago, en el estado en el que está hoy, merece la activación.

Y la clave tiene que ser el id del pago, no el de la notificación. Si deduplicás por el id de la notificación —distinto en cada POST— nunca deduplicás nada: activás tres veces y contás tres ventas.

El orden correcto

resolver  →  filtrar  →  validar  →  reclamar (idempotencia)  →  activar  →  confirmar
export async function POST(req: Request) {
  const { data, type } = await req.json();
  if (type !== "payment" || !data?.id) return json(200, { ignored: true });

  // 1. RESOLVER: el body del webhook no dice el estado. La API sí.
  const pago = await getPayment(String(data.id));
  if (!pago) return json(500, { retry: "todavía no visible" });

  // 2. FILTRAR: refunded y charged_back tienen su propio camino (revocar).
  if (pago.status === "refunded" || pago.status === "charged_back") {
    await revocarAcceso(pago);              // idempotente por su cuenta
    return json(200, { revoked: true });
  }
  if (pago.status !== "approved") return json(200, { skipped: pago.status });

  // 3. VALIDAR el monto contra el precio oficial de esa moneda.
  if (!montoCubrePrecio(pago)) return json(200, { rejected: "monto insuficiente" });

  // 4. RECLAMAR: recién ahora la idempotencia tiene sentido.
  const claim = await reclamarPago("mercadopago", String(pago.id), pago);
  if (!claim.reclamado) return json(200, { already: true });

  // 5. ACTIVAR y 6. CONFIRMAR.
  try {
    await activarAcceso(pago);
    await claim.confirmar();
    return json(200, { ok: true });
  } catch (e) {
    await marcarFallido("mercadopago", String(pago.id), String(e));
    return json(500, { retry: "activación fallida" });
  }
}

Con este orden, la notificación de pending sale por el paso 2 sin tocar la tabla. La de approved llega con la tabla limpia, reclama y activa. La tercera reclama, no consigue, y devuelve 200.

La tabla, y el reclamo atómico

El reclamo tiene que ser atómico contra la base. Un SELECT seguido de un INSERT no sirve: las dos notificaciones de MercadoPago pueden llegar con milisegundos de diferencia a dos instancias serverless distintas, las dos leen "no existe", y las dos activan.

create table public.pagos_procesados (
  rail            text        not null,      -- 'mercadopago' | 'stripe' | 'lemonsqueezy'
  payment_id      text        not null,      -- id del PAGO en el rail, no el de la notificación
  status          text        not null,      -- 'processing' | 'processed' | 'failed'
  error           text,
  user_id         uuid        references auth.users(id) on delete set null,
  monto           numeric(14,2),
  moneda          text,
  creado_en       timestamptz not null default now(),
  actualizado_en  timestamptz not null default now(),
  primary key (rail, payment_id)
);

El reclamo es un solo statement, y la base decide quién gana:

insert into public.pagos_procesados
       (rail, payment_id, status, user_id, monto, moneda)
values ($1, $2, 'processing', $3, $4, $5)
on conflict (rail, payment_id) do update
   set status = 'processing',
       error = null,
       actualizado_en = now()
 where pagos_procesados.status = 'failed'
    or (pagos_procesados.status = 'processing'
        and pagos_procesados.actualizado_en < now() - interval '5 minutes')
returning payment_id;

Tres comportamientos en una sola query:

  • Fila nueva → devuelve el payment_id. Reclamado, seguí.
  • Ya está processed → el where no matchea, no devuelve nada. Ya se hizo, 200.
  • Está failed, o processing hace más de 5 minutos → se re-reclama. Ese segundo caso es un lease: cubre la instancia que se murió entre reclamar y confirmar y dejó la fila trabada para siempre.

Si no devolvió fila, no reclamaste. Simple de leer en el handler y sin transacciones a mano.

No borres la fila cuando falla: marcala

La tentación, cuando la activación explota, es borrar la fila de deduplicación para que el reintento pueda volver a entrar. Funciona, y te deja ciego: no te queda ningún rastro de que hubo un fallo, ni cuál, ni cuántas veces.

export async function marcarFallido(rail: string, paymentId: string, error: string) {
  await supabase
    .from("pagos_procesados")
    .update({ status: "failed", error: error.slice(0, 2000), actualizado_en: new Date() })
    .eq("rail", rail)
    .eq("payment_id", paymentId);
}

La fila queda con status = 'failed' y el mensaje. El reintento de MercadoPago vuelve, el on conflict … where status = 'failed' la re-reclama, activa, y la sobreescribe a 'processed'. La idempotencia nunca se rompió y el historial queda.

Con eso, tu tablero de soporte es una query:

select payment_id, moneda, monto, error, actualizado_en
  from public.pagos_procesados
 where status <> 'processed'
   and creado_en > now() - interval '7 days'
 order by creado_en desc;

Cualquier fila ahí es plata cobrada sin entregar. Es la única alerta de pagos que hace falta tener.

El test que hay que escribir

No testees "el webhook funciona". Testeá la secuencia:

it("activa una sola vez ante pending → approved → approved", async () => {
  mockPayment({ id: "1", status: "pending",  transaction_amount: 39900, currency_id: "ARS" });
  expect((await POST(ipn("1"))).status).toBe(200);
  expect(activarAcceso).not.toHaveBeenCalled();      // pending no activa

  mockPayment({ id: "1", status: "approved", transaction_amount: 39900, currency_id: "ARS" });
  expect((await POST(ipn("1"))).status).toBe(200);
  expect(activarAcceso).toHaveBeenCalledTimes(1);    // ← el que atrapa el bug

  expect((await POST(ipn("1"))).status).toBe(200);
  expect(activarAcceso).toHaveBeenCalledTimes(1);    // el duplicado no suma
});
